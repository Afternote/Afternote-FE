**해소 확인** — 1차 QA #9(TODAY'S QUESTION 고정값) · #17/2차 #5(placeholder `Text Field`) · 2차 #2 부분(상단 바로가기 3종 중 공지사항·수신자 목록 연결). 새벽의 미확정 관찰이던 홈 인사말 "…님" 은 **결함이 아니었다** — 클린 설치 + 서버 무응답이라 이름을 받을 경로가 없던 정상 폴백이고, 로그인 상태에서는 계정 이름이 포함된 인사말로 나온다.

**성공 경로 실측 (17:14~17:26 KST)** — 에뮬레이터에 화면잠금·지문을 등록해 애프터노트 인증 게이트를 통과한 뒤 돌렸다.

- **#706 재발** — CLOSED 이슈인데 **같은 검증 에러가 연속되면 안내가 발행되지 않는다.** 에러 값이 바뀌면 뜨고 같으면 안 뜬다. 후속 #1127 등록.
- **관찰** — 상세 응답이 계정 비밀번호를 평문으로 내려준다. 애프터노트 조회 게이트가 앱 재시작마다 지문을 요구하고, 화면 제목이 '지문 로그인' 인데 실제로는 조회 인증이라 라벨이 어긋난다.

**수신자 열람 흐름 — admin 승인으로 무대를 세워 FE 차단 지점 확인 (18:34 KST)**

2차 QA 이래 '관리자 승인 수단 부재' 로 못 보던 구간을, admin 계정 승인 API 로 열었다. curl 로 서류 제출·승인까지 무대를 세우고 그 뒤를 앱으로 검증하는 방식(무대는 우회, 대상은 앱).

- **admin 승인 경로 실재·동작** — `POST /admin/verifications/{id}/approve` 로 PENDING→APPROVED. 열람 = 사망확인 승인 + 콘텐츠별 전달 조건, 둘 다(AND)여야 열림.
- **#915 = 서버 계약 미반영** — presigned 요청의 `contentLength` 필수화는 BE 커밋 27fa442(8/9). FE DTO 가 안 따라감. curl 로는 성공, 앱은 400.
- **승인 이후 화면이 통째로 막힘 = #607** — 받은 기록함이 `record-boxes` 를 안 써서 서버 APPROVED 를 못 읽는다. 승인해도 카드는 '열람 불가' 고정, 열람 신청은 다시 서류 화면으로. `getDeliveryVerificationStatus()` 는 구현돼 있으나 화면이 호출 안 함. #599·#612 와 한 뿌리.

이 세 개가 겹쳐 **admin 이 승인해도 수신자는 앱에서 기록을 못 본다.** record-boxes 연동(#607) 하나로 대부분 풀린다.

**수신자 열람 API를 직접 열어 응답 대조 (18:5x KST)** — 발신자 토큰으로 전달 조건을 설정하고 관리자 API로 승인한 뒤, 수신자 API 응답을 작성자 원본과 대조했다. #607 때문에 앱의 승인 후 화면으로는 진입하지 못했으므로 FE 종단 간 검증은 아니다.

- **BE #98 회귀 발견** — 수신자가 받는 SOCIAL 애프터노트 상세에 **credentials(계정 ID·비번)가 없다.** 작성자는 테스트용 ID·비밀번호를 저장했지만 수신자 응답 8개 키에 credentials 가 빠진다. `actions:['delete account']` 는 오는데 대상 계정이 없어 사후 계정 인계가 성립하지 않는다. BE #98(2026-07-30 '완료' 로 닫힘)과 동일 증상 → 회귀. BE 레포에 재현 코멘트로 재오픈 요청(담당 sooooa16). **FE 결함 아님.**
- **전달 조건 + 승인 경로 실동작** — AFTERNOTE=RECEIVER_REQUEST 설정 → 서류 재제출 → admin 승인 → 403→200 열림. fulfillByReceiverRequest 가 승인 시 조건을 충족시키는 설계 확인.

**3차 QA는 8/25 예비·핵심 8개 패스까지 수행했고 현재 진행 중이다.** 전체 기능 순회는 완료되지 않았으며, 아래 진척(4절)과 커버리지 갭(5절)을 기준으로 남은 범위를 7절의 향후 계획에서 보강한다.

**주의: 이 표의 "리뷰 실측" 열은 8/23~24 리뷰가 마음의 기록에 집중된 결과다.** 그 이전 상시 QA(1절의 이슈 180건)는 기능별로 귀속돼 있지 않아 이 표에 반영되지 않는다. 따라서 **0 이 "한 번도 안 봤다" 를 뜻하지는 않는다** — 다만 *증거로 되짚을 수단이 없다*는 뜻이다.

그 유보를 감안해도 겹치는 구멍은 뚜렷하다:

- **애프터노트**: 머지 PR 60건으로 최다, 2차 QA 잔여 14건으로 최다. 되짚을 증거는 3건.
- **설정**: 화면 17개로 최다인데 스크린샷 0장 · 증거 1건(차단) · 잔여 9건.
- **마음의 기록**: 유일하게 깊게 파인 영역이지만 스크린샷 baseline 0장이라 시각 회귀는 못 잡는다.

## 6. 운영 규약 — 앞으로 증거를 어디에 남기나

| 무엇을 했나 | 어디에 남기나 |
| --- | --- |
| 회차 QA (전 기능 순회) | `docs/qa/round-<회차>.md` |
| PR 리뷰에서 지적별 실측 | 해당 PR 리뷰 본문의 검증 섹션 |
| 에뮬레이터·실서버 실측 | `docs/qa/evidence/<full-head-sha>.json` |
| 시안·명세에 없어 판단으로 정한 것 | `docs/qa/assumptions.md` |

**정본은 Git으로 추적하는 저장소 문서다.** 런타임 증거의 필드·민감정보 제거 규칙은
[증거 대장 안내](evidence/README.md)를 따른다.
신규·갱신 기록은 저장소 문서에만 남긴다.

**지금 남은 기록상의 구멍:**

1. **증거 규약 도입 전 QA 상당수는 파일이 없다.** 이관으로 새 유실은 막았지만 기록되지 않은 과거 QA는 복원되지 않는다.
2. **상시 QA 는 발견된 결함(이슈)만 남고, "무엇을 봤는데 멀쩡했나" 는 안 남는 경우가 있다.** 회차 QA 문서와 런타임 증거의 `result`·`not_covered`가 이 공백을 메워야 한다.

**원칙: "누가 했나" 는 기록하지 않는다.** 증거 대장은 도구·사람 무관 공용이고, 남아야 하는 것은 *어느 리비전에서 무엇이 검증됐나* 뿐이다.
