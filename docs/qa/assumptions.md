## #627 — TODAY'S QUESTION CTA 목적지

**정한 것**: `MindRecordRoute.DailyQuestionWriteRoute`(데일리질문 답변 작성 화면).

**근거가 없는 이유**: 이슈 본문이 "이 CTA 의 목적지(데일리질문 답변 작성 화면인지 기록 탭인지)가
시안에서 어떻게 정의돼 있는지는 확인하지 않았다" 로 남겨 뒀다. Figma 카드 노드에 프로토타입
연결이 없다.

**판단 근거**: 카드 문구가 "데일리질문 **답변하기**" 이고, 같은 동작의 기존 진입점(기록 탭 →
FAB)이 이 작성 화면이다. 기록 탭으로 보내면 사용자가 한 번 더 눌러야 한다.

**뒤집을 때**: `AppNavigationActions.onAnswerClick()` 의 `navigate(...)` 대상만 바꾼다.

## #442 — 삭제 실패 안내 표현

**정한 것**: 완료 토스트(Figma `2372:25211`)와 같은 자리·같은 모양에 문구만 다르게.
`"%1$d개를 삭제하지 못했어요. 다시 시도해 주세요."`

**근거가 없는 이유**: 시안에 삭제 **실패** 상태가 없다. 완료 토스트만 정의돼 있다.

**판단 근거**: 새 표현을 만들면 미확정 디자인이 제품 동작으로 굳는다. 이미 있는 컴포넌트를
재사용하고 문구만 바꾸는 쪽이 되돌리기 쉽다.

**뒤집을 때**: `DraftDeleteFailedToast` 컴포저블과 문자열 리소스만 교체한다. 상태 모델
(`DraftDeleteOutcome.SomeFailed`)은 표현과 무관하게 유지된다.

비활성 "선택 삭제" 라벨 색(`gray6`)도 같은 이유로 임시값이다.

## #716 — 실패·진행 표현

**정한 것**: 새 컴포넌트를 만들지 않고 기존 텍스트 표시에 문구와 재시도만 붙였다.

**근거가 없는 이유**: 실패 안내 컴포넌트의 표현 통일은 이슈 노트대로 #446 범위다.

**판단 근거**: 지금 새 표현을 만들면 #446 이 확정될 때 두 벌이 된다. 동작(재시도 결선·
문구 치환)만 고치고 표현은 그대로 뒀다.

## #592 — 오늘의 추천 질문 조회 실패

**정한 것**: `getToday()` 가 실패하면 그 영역을 그리지 않는다.

**근거가 없는 이유**: 시안에 이 영역의 실패 상태가 없다.

**판단 근거**: 목록 자체는 정상인 상황이라 보조 영역 하나 때문에 화면을 오류로 바꾸는 것은
과하다. 다만 이슈가 "실패가 드러나지 않는다" 를 지적한 것은 그대로 남는다.

**뒤집을 때**: `TodayRecommendedQuestion` 하나만 고치면 된다.

## #751 — 날짜 파싱 실패 항목 처리

**정한 것**: 목록에서 제외한다(내용도 함께 안 보인다).

**근거가 없는 이유**: 이슈가 세 선택지(제외 / 날짜 자리 비움 / 상위로 전파)를 제시하고
고르지 않았다.

**판단 근거**: 같은 파일의 `Diary.toUi()` 가 이미 "제외" 규칙을 쓰고 KDoc 에 근거가 있다.
새 정책을 만들기보다 갈라진 쪽을 맞추는 편이 낫다고 봤다.

**뒤집을 때**: 내용을 살리려면 `DailyQuestion.date` 를 nullable 로 바꾸고 카드가 날짜 자리를
비우게 한다.

## #789 — 기분 enum 의 "모르는 값" 처리

**정한 것**: 기분 필드의 **키 누락**은 파싱 실패로 두되, 클라가 모르는 **값**은
그 칸만 비운다. nullable 기분 필드(`weeklyDominantMood`, `week[].emotion`)에
`NullableTodayMoodSerializer` 를 달아 모르는 값을 `null` 로 접는다.

**근거가 없는 이유**: 이슈는 "기본값을 없애 계약 누락을 드러내라" 까지만 정했다.
그런데 `coerceInputValues` 는 생성자 기본값이 있어야 동작해서, 기본값을 걷어내면
키 누락뿐 아니라 값 확장까지 함께 실패로 바뀐다. 이슈가 이 부수 효과를 다루지 않았다.

**판단 근거**: 두 상황은 성격이 다르다. 키 누락은 계약이 바뀐 것이라 드러나야 하지만,
값 확장(서버가 기분 종류를 늘리거나 표기를 바꾸는 것)은 이모지 한 칸 대신 그 주/그 달
목록 전체를 날릴 일이 아니다. 감정 값이 한글로 관측된 전례도 있다 (#591).

**남는 위험**: 비-nullable 인 일기 항목의 `todayMood` 는 이슈 지시대로 non-null 이라,
모르는 값이 오면 **그 달 목록 전체**가 실패한다. 사용자가 3종 중 고르는 값이고 실서버가
`"SOSO"` 형태로 내려주는 것은 확인했지만, 서버가 종류를 늘리면 여기서 먼저 깨진다.

**뒤집을 때**: `DiaryListItemDto.todayMood` / `ReceiverDiaryItemDto.todayMood` 도
nullable 로 낮추고 같은 직렬화기를 달면 된다 (도메인 `Diary.todayMood` 까지 전파).

## #729 — 과거 주간리포트를 어디까지 제공할지

**정한 것**: 이번 주 포함 **52주(1년)**.

**근거가 없는 이유**: 이슈는 "고정 상수 5개가 아니라 제품에서 허용하는 과거 주간리포트
범위" 라고만 적었고, 그 범위가 얼마인지는 명세·시안 어디에도 없다. 시안의 열린 메뉴는
가시 항목 5개와 스크롤 표시만 보여줄 뿐 전체 개수를 알려주지 않는다.

**판단 근거**: 계정 생성 주까지로 좁히는 쪽이 가장 정확하지만 서버에 가입일이 없다
(`GET /users/me` 는 이름·이메일·전화·프로필만 준다). 기록이 없는 주를 골라도
`GET /mind-record` 는 0 건으로 정상 응답하므로 빈 주차를 보여주는 것 자체는 안전하고,
1년이 "지난 리포트를 돌아본다" 는 화면 목적에 무난한 상한이라고 봤다.

**뒤집을 때**: `WeeklyReportWeekOptions.kt` 의 `WEEK_OPTION_COUNT` 하나만 바꾸면 된다.
가입일 API 가 생기면 `buildWeekOptions(today, count)` 의 `count` 를 가입 주까지의 주 수로
계산해 넘기면 되고, 메뉴 높이(가시 항목 수)는 이 값과 무관하게 유지된다.

## #725 — 부분 실패를 어떤 상태로 볼지 / 폴링 간격

**정한 것 1**: `pending == 0 && succeeded > 0 && failed > 0`(일부만 실패)은
**완료**로 본다 — 건진 키워드를 그대로 보여준다.

**근거가 없는 이유**: 이슈는 "분석 대기, 분석 실패, 분석 완료, 실제 분석 대상 없음"
네 상태만 요구하고, 부분 실패가 어느 쪽인지는 정하지 않았다.

**판단 근거**: 실패 화면으로 덮으면 이미 성공한 키워드까지 가린다. "아무것도 건지지
못한 경우"만 실패로 두는 편이 손실이 적다고 봤다.

**뒤집을 때**: `EmotionAnalysis.status` 의 `succeeded == 0 && failed > 0` 조건 하나다.
부분 실패를 따로 표시하려면 `PARTIALLY_FAILED` 를 추가하고 카드에 분기를 하나 더 둔다.

**정한 것 2**: 분석 완료를 기다리는 재조회는 **8초 × 8회(약 1분)** 로 끊는다.

**근거가 없는 이유**: 분석 완료를 알려주는 채널(푸시·웹소켓·완료 플래그)이 없고,
분석이 보통 얼마나 걸리는지도 명세에 없다. 실측(2026-08-23)에서는 일기 1건이
1분 넘게 `pending` 이었고 그 세션에서는 끝나지 않았다.

**판단 근거**: 무한 폴링은 하지 않는다는 것만 확실했다. 화면에 머무는 동안 한 번은
잡을 만한 길이로 1분을 뒀고, 그 뒤는 화면 이탈·복귀(`refreshOnReturn`)와 사용자의
재시도 버튼에 맡긴다.

**뒤집을 때**: `WeeklyReportViewModel` 의 `EMOTION_ANALYSIS_POLL_ATTEMPTS` /
`EMOTION_ANALYSIS_POLL_INTERVAL_MILLIS` 두 상수다. 서버가 완료 신호를 주게 되면
(Afternote-BE#117) `awaitEmotionAnalysis` 를 그 구독으로 갈아끼우면 된다.

**남는 것**: FE 의 "다시 시도" 는 **재조회**일 뿐 서버 측 재분석 트리거가 아니다.
재시도 소진(`failed`) 상태에서 다시 분석을 걸 방법은 아직 없다 — Afternote-BE#117 소관.

## #547 — 주간리포트 날짜 파싱 실패 처리

**정한 것**: 해석하지 못한 날짜의 항목은 **DTO→도메인 경계에서 제외**한다.
도메인 `WeeklyReportDailyQuestion.date` 는 non-null `LocalDate` 로 올린다.

**근거가 없는 이유**: 이슈가 "실패 처리 정책(제외 / nullable 로 노출 후 UI 에서 날짜
비우기 등)을 한 곳에서 정한다" 라고만 적고 어느 쪽인지 고르지 않았다.

**판단 근거**: 같은 모듈이 이미 "제외" 로 수렴하고 있다 — `Diary.toUi()`,
`DailyQuestion.toUi()`(#751) 가 날짜를 못 정하면 항목을 뺀다. 새 정책을 하나 더
만들기보다 갈라진 쪽을 맞추는 편이 낫다고 봤다. 종전의 `LocalDate.now()` 폴백은
파싱 못 한 기록을 **오늘 작성한 것처럼** 보여 이상을 감추므로 어느 쪽으로 가든 폐기 대상이다.

**남는 위험**: 날짜만 깨진 항목의 제목·본문까지 함께 사라진다. 실서버는 늘
`yyyy.MM.dd 요일` 로 내려주고 세 포맷을 모두 허용하므로 실제로 걸릴 일은 적지만,
서버가 포맷을 바꾸면 HISTORY 가 통째로 비는 방향으로 실패한다. 매퍼가 로그를 남긴다.

**뒤집을 때**: `WeeklyReportDailyQuestion.date` 를 `LocalDate?` 로 낮추고
`toDomainOrNull()` 을 `toDomain()` 으로 되돌린 뒤, 카드가 날짜 자리를 비우게 한다.
집계는 이미 `mapNotNull` 이라 그대로 두면 된다.

## #618 · #614 — 수신자 화면의 구성과 문구

**정한 것 1 (#618)**: 받은 기록 본문을 **별도 라우트가 아니라 바텀시트**로 연다.
구성은 날짜·기분 → 제목 → 본문 순.

**근거가 없는 이유**: 이슈가 시안 미대조다. 수신자 기록 상세 화면의 시안이 있는지
확인하지 못했다.

**판단 근거**: 이 화면에는 뒤로가기가 없어(#614) 새 화면을 쌓으면 시스템 백키 외에
나올 방법이 없다. 시트는 스와이프·바깥 탭으로 닫힌다. 같은 모듈의 `MemoryDetailOverlay`
가 이미 쓰는 방식이기도 하다.

**뒤집을 때**: `ReceiverRecordDetailSheet` 한 컴포넌트만 고치면 된다. 라우트로 옮기려면
`MindRecordRoute` 에 항목 ID 를 받는 라우트를 더하고 화면에서 시트 호출을 네비게이션으로
바꾼다.

**정한 것 2 (#614)**: 전달 조건 미충족(403 / code 2009) 문구를
«아직 열람할 수 있는 기록이 없어요. 작성자가 전달 시점을 정하면 이곳에서 볼 수 있어요.»
로 적었다.

**근거가 없는 이유**: 이슈가 «대체 문구를 확정할 때 디자이너 확인이 선행돼야 한다» 고
명시했다. 확인을 받지 못했다.

**판단 근거**: 원문("아직 전달 조건이 충족되지 않았습니다")은 사용자가 무엇을 기다리는지
알 수 없다. 수신자가 할 수 있는 일이 없는 상태이므로 **기다리는 상태임과 누가 정하는지**를
알리는 쪽으로 적었다.

**뒤집을 때**: `mindrecord_receiver_delivery_not_ready` 문자열 하나다.

**남는 것**: 두 이슈 모두 **실기기 종단 확인을 하지 못했다.** 수신자 기록 화면은
열람 승인(`delivery-verification` APPROVED)된 계정이 있어야 열리는데, 승인은 관리자만
할 수 있고 수신자·발신자 API 어디에도 승인 경로가 없다. 403 응답 자체는 재현했고
(수신자 생성 → `X-Auth-Code` 조회 → `403 {"code":2009}`), 화면 동작은 Robolectric
Compose 테스트로 고정했다.

## #207 — 깊은 생각 제거 후 홈 요약 그리드 레이아웃

**정한 것**: `WeeklySummaryGrid` 의 «최근 깊은생각» 카드를 없애고, 오른쪽에 남은
«이번 주 기록 수» 카드가 **왼쪽 큰 카드와 같은 높이**를 채우게 했다 (3장 → 2장).

**근거가 없는 이유**: 깊은 생각 제거는 기획 결정으로 전달받았지만, 카드가 빠진 뒤의
그리드 시안은 받지 못했다.

**판단 근거**: 오른쪽 컬럼은 «작은 카드 2장 + 간격» 이 왼쪽 큰 카드 높이와 같도록
짜여 있었다. 한 장만 남기고 아래를 비우면 그리드가 어긋나므로, 남은 한 장을 늘려
2열 구성을 유지하는 쪽을 택했다.

**뒤집을 때**: `WeeklySummaryGrid` 한 파일이다. 카드를 다른 것으로 채우기로 하면
오른쪽 컬럼을 다시 `smallSquareSize` 두 장으로 되돌리면 된다.

**함께 정리한 것**: 서버는 `deepThoughtAmount`·`week[].type=DEEP_THOUGHT` 를 계속
내려준다. **DTO 에 선언하지 않아 그대로 무시**하고(#207), 기록일수 집계에서도
제외한다(#590). 서버가 나중에 필드를 빼도 앱은 영향받지 않는다.

## #955 일기 수정 요청의 수신자 — "빈 선택" 의 뜻

서버는 `receiverIds` 를 세 가지로 읽는다(실측): 목록이 오면 그대로 반영, **생략하면 기존
유지**, **빈 목록이면 전체 해제**.

문제는 수정 화면 프리필이 기존 수신자를 불러오지 않는다는 것이다. 그래서 화면의 "고른 게
없음" 이 "원래 없었음" 인지 "사용자가 다 뺐음" 인지 구분되지 않는다.

**빈 선택은 생략(null)으로 보내기로 했다.** 빈 목록으로 보내면 수신자를 건드리지 않은
편집이 기존 지정을 지우고, 목록 응답에 수신자가 없어 되살릴 수도 없다. 반대로 생략을
고르면 잃는 것은 "전체 해제" 기능뿐이다 — 애초에 프리필이 없어 사용자가 표현할 수도 없던
동작이다. 생성 경로(#933)와도 같은 규칙이 된다.

프리필까지 붙으면(#759 가 목록 응답의 `receivers` 를 도메인에 싣는다) 빈 선택을 해제로
해석하는 쪽으로 바꿀 수 있다.

**분리한 것** — 일기의 기록 날짜는 생성·수정 어느 쪽으로도 서버에 보낼 수 없다(양쪽
스키마에 `date` 없음, 보내도 무시됨을 실측). 날짜 선택이 표시 전용인 문제는 BE 계약
확장이나 기획 결정이 필요해 #1008 로 분리했다.
