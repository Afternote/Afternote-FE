리팩토링 작업 단위 결정 시, 본 PR 에서 만드는 코드가 *다음 PR (Phase 2 등) 에서 제거 대상* 인지 먼저 점검한다. 제거 대상이면 본 PR 작업을 *건너뛰고* 근본 해결로 직행. 분할 안 함.

**Why:** 두 비용 trade-off + 우선순위 — (1) PR 합본 시 *팀원이 큰 PR 을 리뷰하는 부담* ↑, (2) PR 분할 시 *본인이 Android Studio 커밋 탭에서 throw-away 코드를 직접 검토하는 시간 낭비* (어차피 다음 PR 에서 사라질 코드를 자기 확인). 사용자(1hyok) 가 명시(2026-05-23): "리뷰가 많아지는 것보다 내가 없어질 코드를 보고 있는 병신 짓을 하지 않는 것이 훨씬 중요함." 즉 **팀원 리뷰 부담 증가는 의식적으로 감수** 하고 throw-away 자기 검토 회피를 우선. 일반적인 PR 분할 권장 정신 (작은 PR ↑ 리뷰 부담 ↓) 보다 본 우선순위가 위.

**합본 임계 크기 (사용자 명시, 2026-05-24): ~50 파일**
- 합본 시 변경 파일 수가 ~50 이하 → throw-away 회피 우선, **합본 강제**.
- 50 초과 → 합본 자체가 PR 한 개에 무리 → 분할 허용 (예: #228 의 전수 9 VM 마이그레이션 같은 극단 케이스).
- 작업 분석 단계에서 합본 시 예상 파일 수를 *사전 추정* 해서 본인에게 짧게 보고 (분할 여부 판단 근거).

**How to apply — throw-away 의심 시점에 *즉시 PR 합본 전환*** (사전·사후 동일):
- **사전 인지**: 새 refactor 이슈 검토 시 본문에 "Phase 1 / Phase 2", "임시 격리 / 근본 분리", "별도 후속 PR" 같은 단계 구분 또는 키워드가 있으면 → *Phase 1 산출물이 Phase 2 에서 제거 대상* 인지 확인. 제거되면 Phase 1 건너뛰고 Phase 2 직행. 한 번만 확인 후 진행.
- **사후 인지**: 작업 도중 *throw-away 변경분을 만들 신호* 발견 (예: "이 utility 는 다음 PR 에서 사라질 것" 같은 KDoc 작성 중, 또는 변경 영역이 다음 단계에서 재작성될 게 명백) → *즉시 멈추고* 현 작업 폐기 + 근본 방향(=PR 합본) 으로 전환 제안.
- **결과는 동일**: 사전이든 사후든 → PR 합본으로 throw-away 코드 자체를 만들지 않음. 본인이 커밋 탭에서 throw-away 검토할 상황 없음.
- 본인 우선순위 (위 Why) 따라 단순 "PR 작게 쪼개라" 권장을 분할 사유로 들지 않음.
- 예외 — *동작 격리* (예: feature flag 뒤 점진 도입, 호환성 deprecated 단계 등) 처럼 Phase 1 산출물이 *제거되지 않고 영구 유지* 되는 분할은 throw-away 아님 → 본 정책 적용 대상 아님.
